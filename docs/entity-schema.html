How it fits together

Four concentric rings. workspaces scopes everything; entities is the hub; identity, history and relationships hang off entities.uuid; FTS shadows the text.

The one edge that matters most. events.entity_uuid is NOT NULL REFERENCES entities(uuid) with no ON DELETE clause, and every one of the 579 entities has at least one event row. No entity can be deleted. Archival is the only available terminal operation — which the append-only design arguably intends, but nothing in the API says so.

CREATE TABLE "entities" (
            uuid           TEXT NOT NULL PRIMARY KEY,
            workspace_uuid TEXT NOT NULL
                           REFERENCES workspaces(uuid),
            type_id        TEXT NOT NULL,
            entity_id      TEXT NOT NULL,
            name           TEXT NOT NULL,
            status         TEXT,
            parent_uuid    TEXT REFERENCES "entities"(uuid),
            artifact_path  TEXT,
            created_at     TEXT NOT NULL,
            updated_at     TEXT NOT NULL,
            metadata       TEXT,
            type           TEXT NOT NULL DEFAULT 'work',
            kind           TEXT NOT NULL DEFAULT 'feature',
            lifecycle_class TEXT NOT NULL DEFAULT 'feature_flow',
            UNIQUE(workspace_uuid, type_id),
            CHECK (
                (type='workspace' AND kind='workspace') OR
                (type='brainstorm' AND kind='brainstorm') OR
                (type='container' AND kind='project') OR
                (type='work' AND kind IN (
                    'feature','backlog','bug','initiative','objective','key_result','task'
                ))
            )
        )

SELECT
  ent.uuid AS entity_uuid,
  (SELECT to_value  FROM entity_axis_state s WHERE s.entity_uuid = ent.uuid AND s.axis = 'pipeline')  AS pipeline_value,
  (SELECT timestamp FROM entity_axis_state s WHERE s.entity_uuid = ent.uuid AND s.axis = 'pipeline')  AS pipeline_at,

append_phase_event writes three tables at once. It inserts into phase_events, updates entities.status, and touches workflow_phases — and it is the only sanctioned status write path. It does not consult the lifecycle machine, which lives in router.py, so it will persist a status the machine forbids.
Two event stores are written by different actions. append_phase_event feeds v1-era phase_events (1,445 rows, no foreign key). append_event feeds the v2 immutable events core (2,195 rows, FK to entities). Nothing writes both as a single transaction by default.
delete_entity touches five tables and completes none of them. It cascades entity_tags, entity_okr_alignment, entities_fts and workflow_phases before removing the entity row — but the events.entity_uuid foreign key aborts the transaction, so in practice the whole operation rolls back for every entity in the database.
The allocator reads entities to write sequences. next_sequence_value bootstraps its counter by scanning entity ids with a regex, which is why a stale counter and a text-shaped id can collide. A count taken from entity_display.seq would be structural.
Orchestrators own no SQL. allocate_entity_id, complete_phase, transition_phase, run_backfill and sync_entity_statuses issue no statements of their own — every row in their line is inherited from what they call. That is why the r/w shading matters: it separates what an action does from what it causes.

Integrity observations

Findings from inspecting the live database, relevant to any ground-up redesign.

Display identity is 69% covered. 180 of 579 entities have no entity_display row — 166 legacy backlog ({NNNNN}, no slug), 10 projects (the P prefix defeated the backfill), 3 brainstorms, 1 feature. Numbering logic that joins this table silently under-counts.
Four id shapes coexist. {NNN}-{slug}, P{NNN}-{slug}, bare {NNNNN}, and {YYYYMMDD}-{slug}. At least six code sites parse them, and they disagree about three of the four.
The registration gate rejects real data. register_entity enforces ^\d+-.+ in production, which no project id satisfies — neither the documented P{NNN} nor the actual P{NNN}-{slug}. It has been this way since 2026-05-15.
The lifecycle machines do not match the data. The backlog machine permits exactly one transition (open → dropped), yet live rows hold promoted and archived. Projects have no archived phase at all. append_phase_event writes status without consulting the machine, so validation and persistence disagree.
