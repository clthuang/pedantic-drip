## 4. Review budgets

**Is a scoped re-review implementable by a fresh-context reviewer?** Yes, if the input and the output schema enforce the scope, not the prose. The re-reviewer receives: the prior findings JSON (ids, file:line, text), `git diff <reviewed commit>..HEAD -- shape.md plan.md`, and read access to the artifact for context. Its schema is keyed by finding: `{findings: [{id, status: resolved | open | regressed, evidence}], new_in_diff: [{...}]}`, with `new_in_diff` allowed only for a defect inside a hunk. Codex's adversarial review takes a brief like this well; a fresh agent is better at it than a continuing one, because it has no memory of what it meant. The conductor's existing reviewer-claim verification (§A3:108) still applies to every finding. **Fix S:** write that schema into §A4:139 beside `{approved, issues[], summary}`, so the first and later passes return different shapes and nobody can run a full review by accident.

**What it costs for a medium feature** (estimates, to be replaced by the first `metrics` entries): a first-pass design or test-case review on `gpt-6-astra` at `xhigh`, with codebase grounding, is in the order of 200–400k tokens, mostly cached input; a scoped re-review 50–100k. Calvin rounds are similar to a scoped pass each. Three stages: typical 1 full + 1 scoped each, about 0.9–1.2M tokens and 6 reviewer calls; worst case 1 full + 2 scoped each, about 1.2–1.8M and 9 calls. The old 3–5 rounds were full passes inside the main context; the token total is in the same band, but the main context now holds only the JSON results, which is the cost the user actually felt ("eat large parts of the context"). `pd-status --compare` is deferred, so the first ten features' `metrics` entries are the only way to know; the plan already writes them (§6:632).

**A cheaper way to the same assurance, inside the ruling:**
- **End-early is already the rule** (§A2:57); make sure the conductor does not revise and re-submit on warnings alone. One line in the skill: "a pass with no blocker ends the stage, whatever its warnings say".
- **For `mode: small`, review Contracts and Plan in one call.** The user already allows writing them in one sitting (§A2:73); reviewing them in one sitting follows, and saves one first pass per small feature. Both are still checked.
- **Batch the rejections, never re-review them.** A finding the conductor rejects with file:line goes to the user's batch (§A4:136 already does this after code); before code it should too, rather than costing a scoped cycle to argue with the reviewer.
- **Don't drop to a cheaper model for re-reviews.** Principle §6 says verification does not degrade gracefully; the scope, not the model, is what makes cycle 2 cheap.

## 6. Weight and readiness

**A medium feature (4 tasks, `standard`) after D14:**
- **Agents:** typical 16 (calvin ×2, codebase-explorer ×1, design review ×2, test-case review ×2, implementers ×4, merger ×1, code review ×1, QA ×1, fixer ×1, QA re-run ×1); worst case 27 (three cycles at each of the three pre-code stages, two escalations, three fix cycles, security reviewer, retro-facilitator). Review 3 counted 12/20; D14 added about 4 typical and 7 worst case, all of it review cycles the user chose.
- **Gates:** `phase-gate.sh` ×6 (with `verify`), `pd-lint` on every artifact commit, the Stop gate every turn, the merger's three checks per task, the QA battery ×(1 + fix cycles).
- **Files:** README.md, log.md, shape.md, plan.md, retro.md (conditional), backlog.md, `.claude/pd.local.md`; scratch args; `~/.claude/pd/init-declined`. Seven committed.
- **Entry kinds:** 11 (§6:630).
- **Named rules:** about 22 (the two-commit rule, the stub clause, per-task merger check, refactor mark, flake re-run, three pre-code cycles with scoping, one review pass after code, three fix cycles, judgement-finding test, escalation as cycle 2, rejection stays open, `from_shape`, `small_feature_tasks`, four retro triggers, three hard stops, "or the user has said to stop", `stop_hook_active`, background yield, the token measure, risk tags and their clearing, one goal per feature, the B-id coverage lint).

**Express is now heavier than its definition.** "A small diff on a known pattern, provable by one command" (§A2:72) still runs Codex review, the full QA battery and a three-cycle fix loop. Not a contradiction, but the one place the weight is plainly out of proportion. **Fix S:** for `express`, Verify is the proving command plus the QA battery; the code review is the conductor's call, recorded as a `decision` entry when skipped.

**Readiness.** Calvin can run once §2 is swept (nine S edits, under an hour). The build should not start until §3's four K-rules are written into §A4 and Part B §9, because they define the one check that every other rule leans on, and the bake-off (§16 step 4) will otherwise test prose. **The single biggest remaining risk:** the merger's check passes for the wrong reason on day one: a stub-green test counted as proof, a jest suite that "failed as a test" by not loading, an integration break that surfaces one stage late. No agent in the pipeline is placed to see any of those, and the plan's own record (§A8.1:262) says this class is "100% gate-caught / 0% prevented". Make the gate mechanical (`pd-proof`), and it is caught.
